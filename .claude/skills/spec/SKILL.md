# /spec — 기능 스펙 작성 (1단계)

기능 하나의 **무엇을·왜**를 정리해 GitHub 이슈로 올린다. 기획자가 이 이슈를 컨펌해야 `/code`로 넘어갈 수 있다.
입력(`$ARGUMENTS`)은 기능 설명이거나, 수정할 기존 스펙 이슈 번호(`#12`)다. 입력은 이 대화 안에 있으니 되묻지 않는다. 비어 있을 때만 한 번 묻는다.

## 파이프라인

```text
/spec → [기획자 컨펌] → /code → /review → /pr → [개발자 컨펌]
```

스펙의 단일 출처는 **GitHub 이슈 본문**이다. 파일을 만들지 않는다. 대시보드가 이슈를 읽어 보여 준다.

## 절차

1. **맥락 읽기**: `AGENTS.md`, `README.md`, `docs/prd/prd.md`(있으면)를 읽는다. 스펙은 PRD의 어느 항목에서 나왔는지 근거(`PRD §번호`)를 단다. PRD가 없으면 그 사실을 알리고 입력만으로 쓴다.
2. **기존 이슈 확인**: 번호가 주어졌으면 `gh issue view N --json title,body,labels,comments`로 읽고 개정한다. 아니면 `gh issue list --label spec --state all --search "<키워드>"`로 중복을 확인하고 있으면 사용자에게 알린다.
3. **스펙 작성**: 아래 템플릿을 한국어로 채운다. 모호한 곳은 합리적으로 추정하되 `[확인 필요]`로 표시해 기획자가 볼 수 있게 한다. **구현 방법(클래스·테이블 설계)은 쓰지 않는다.** 단, 서버 프로젝트이므로 API는 "초안" 수준의 URL·메서드·주요 필드까지만 적는다.
4. **미리보기 후 확인**: 제목과 본문을 사용자에게 보여 주고, 올려도 되는지 확인한다. 확인 전에는 이슈를 만들지 않는다.
5. **이슈 등록/수정**
   - 라벨이 없으면 만든다 (이미 있으면 무시):
     `gh label create spec --color 5319e7 -d "기능 스펙"`, `stage:spec`(fbca04, 기획자 컨펌 대기), `stage:approved`(0e8a16, 기획자 컨펌 완료), `stage:changes`(d93f0b, 수정 요청), `stage:coding`(1d76db), `stage:review`(c5def5), `stage:pr`(bfdadc)
   - 새 이슈: `gh issue create --title "<제목>" --body-file <파일> --label spec --label stage:spec`
   - 개정: `gh issue edit N --body-file <파일> --remove-label stage:changes --add-label stage:spec` 후 개정 요약을 `gh issue comment N`으로 남긴다.
   - 본문은 임시 파일로 만들고 끝나면 지운다.
6. **보고**: 이슈 URL과 대시보드 주소(`docs/ai/dashboard.json`의 `dashboardUrl`)를 알리고 "기획자가 대시보드에서 승인하면 `/code N`으로 진행할 수 있다(반영까지 최대 10분)"고 안내한다. 개정이면 이전 승인은 무효이므로 재승인이 필요하다고 알린다. 담당자는 `--assignee @me`로 지정한다.

## 스펙 본문 템플릿

```markdown
> 상태: 기획자 컨펌 대기 · PRD 근거: §<번호> · 버전: 1.0.0

## 배경과 목표
왜 필요한가, 성공 기준은 무엇인가.

## 사용자 시나리오
- 사용자는 …하면 …된다.

## 요구사항
| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| FR-1 | … | 필수 |

## API 초안
| 메서드 | URL | 설명 |
| --- | --- | --- |
| GET | /api/v1/… | … |

## 예외·엣지 케이스
- 입력이 잘못되면 …, 데이터가 없으면 …

## 범위 밖
- 이번에 하지 않는 것.

## 완료 조건
- [ ] FR-1 …
- [ ] 예외 케이스가 400/404 등 공통 응답으로 내려간다
```

## 규칙

- 요청받은 기능 하나만 다룬다. PRD 전체를 스펙으로 쪼개 한꺼번에 올리지 않는다.
- 이슈 제목은 한글 명사형(예: `투표 생성 API`). 코드나 브랜치는 만들지 않는다.
- 비밀 값, 개인 정보는 쓰지 않는다.
- 승인은 **기획자가 대시보드에서** 한다. 에이전트는 승인 라벨을 붙이거나 승인 기록을 만들지 않는다.
